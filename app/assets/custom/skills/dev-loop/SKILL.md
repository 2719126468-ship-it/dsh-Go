# 开发闭环

一句话：先判型，再跑最小闭环，最后给可核查的完成证据。别跳步，别"看着像完了"。

## 判型

| 信号 | 分支 |
|---|---|
| 报错、崩、慢、回归 | 排障 |
| 审分支/PR/未提交改动 | 审查 |
| 要拆模块、定接口、找缝 | 设计 |
| 新功能要测试先行 | TDD |
| 查文档/API/一手来源 | 调研 |
| merge/rebase 冲突 | 冲突 |
| 要人点后台/填密钥/做迁移 | 交人 |

## 排障

1. **复现**：把触发条件压到最短（一条命令 / 一个请求 / 一个用例）。复现不了就先加观测，不猜。
2. **二分**：在"确定错"与"确定对"之间切一刀，逐刀收窄。看的是证据不是直觉。
3. **归因**：找到首个错误点，写下"为什么会错"的一句话解释；解释不了说明还没定位到。
4. **修因不修症**：改根因；顺手把同模式的其他调用点一起看一遍。
5. **回归**：原复现步骤跑绿 + 相邻功能跑一遍；跑不了就明说没跑。

## 审查

- 先定 fixed point：`git diff <base>...HEAD` 的范围要写清。
- 两个轴分开看：**规范**（是否符合本仓库既有写法）与**意图**（是否真解决了要解决的问题）。
- 输出按严重度排：阻断 / 应修 / 建议。每条附文件与行号。
- 没问题是结论；无测试覆盖本身算一条风险。

## 设计

- 只定共享词汇、模块边界、缝在哪，不写实现。
- 输出：模块名、对外接口、依赖方向、为什么这样切、什么情况下要重切。
- 接口要深：调用方少知道一件事，就少一个将来会错的地方。

## TDD

红 → 绿 → 重构，每步都小：

1. 写一个**会失败**的测试，跑一遍确认它真的失败（不是编译错）。
2. 最小实现让它绿，不顺手加需求。
3. 在绿的前提下重构，测试保持绿。
4. 集成测试优先打在真实边界（文件系统、HTTP、数据库），别把实现细节焊进断言。

## 调研

- 只要一手来源：官方文档、源码、规范、release notes。二手博客只用来找线索。
- 每条结论带出处链接；版本号与日期写清，API 会变。
- 查不到就写"未找到"，不要用印象补空。

## 冲突

- 先看清两边意图，再决定保留谁；不要机械地取一边。
- 解完必须能构建/跑测试；跑不了就标出风险点。

## 交付格式

```
改动：<文件>:<行> <一句话>
验证：<跑过的命令> → <结果>
未做：<没跑/没覆盖的部分与原因>
```
